# Backboard Right Panel: Current State

## Overview

This document describes what the Backboard right panel is in the current codebase, not a future target design.

The Backboard right panel currently exists as a dedicated VS Code webview view contributed by the `extensions/backboard` extension. Its view id is `backboard.panel`, and it is opened by commands like `backboard.openRightPanel`, `backboard.openPanel`, `backboard.newChat`, and `backboard.showHistory`.

Its job is to provide a compact, persistent chat and control surface for Backboard inside the IDE side area. It is separate from the native VS Code `ChatWidget`; it is custom HTML, CSS, and JavaScript generated by the extension and backed by a local `backboard-bridge` process.

At the moment, the panel is the real execution surface for Backboard runs in the editor. It currently handles:

- Sign in to Backboard.
- Select model, provider, mode, and turn settings.
- Send prompts.
- Stream assistant responses.
- Run local tool calls requested by the model.
- See tool progress and output.
- View generated media or voice output.
- Review file changes.
- Manage recent chats and history.
- Mirror live state into Advanced/Optimus mode.

Advanced/Optimus is not the primary executor. In the current architecture it is a higher-level control and mirror surface. It can send commands to the right panel path and observe live state, but the right panel extension and bridge own the real prompt execution, streaming, local tools, settings, auth, and model metadata.

## Main Implementation

The main implementation lives in `extensions/backboard/src/extension.ts`.

Key pieces:

- `BackboardPanelProvider`: owns the webview and prompt lifecycle.
- `panelHtml(...)`: returns the embedded UI HTML, CSS, and JavaScript.
- `BackboardBridge`: manages the local bridge child process.
- `renderBridgeEvent(...)`: maps bridge events into panel UI updates.
- Optimus handoff functions: command watcher plus live-state and metadata writers.

## Current UI

The panel UI is generated inline by `panelHtml(...)` in `extensions/backboard/src/extension.ts`. There are no separate frontend source files for this UI at the moment.

The current UI is a full-height side panel. It contains:

- Recent chat tabs.
- Status bar with run timer.
- Chat log.
- History pane.
- Composer.
- Model and mode popovers.
- Tool output groups.
- Auth overlay.
- Media, voice, file-change, usage, and question cards when those events appear.

The composer lets the user choose or toggle:

- Mode: `agent`, `ask`, `manual`, `free`.
- Model and provider.
- Reasoning intensity.
- Web search.
- Image generation.
- Voice mode.
- MCP intents such as Figma, Notion, and Google.
- Stop/cancel.
- Send.

When the user is not authenticated, the UI is blurred behind an auth overlay and offers SSO sign-in. The panel also writes model metadata for Advanced/Optimus after auth/config/model state changes.

## Prompt Lifecycle

When the user sends a prompt, the webview JavaScript posts a message to the extension host:

```js
vscode.postMessage({ type: 'send', chatId, prompt, workspace, options });
```

The extension receives this message in `resolveWebviewView(...)`, calls `runPrompt(...)`, and then calls `sendPrompt(...)`.

`runPrompt(...)` serializes prompt execution. If a prompt is already running, the current run is cancelled or allowed to finish before the next one starts. This keeps the visible panel from running overlapping turns in the same webview.

`sendPrompt(...)` resolves:

- Effective workspace.
- Effective chat id.
- Provider and model.
- Mode.
- Reasoning intensity.
- Web search mode.
- Image generation mode.
- Voice mode.
- MCP call hints.
- Local tool list.
- Backboard config.

It then calls the local bridge with the `sendPrompt` command.

There is also a direct Optimus path. If Advanced/Optimus sends a prompt while the webview is unavailable or the command is forced direct, `submitPromptFromOptimus(...)` calls `runOptimusPromptDirect(...)`. That path still uses the same bridge but skips live webview rendering and writes status/transcript updates through the Optimus live-state file.

## Current Streaming Model

Streaming is event-based.

The extension starts a local `backboard-bridge` child process. Requests are JSON lines written to bridge stdin. The bridge writes JSON lines back on stdout. Each parsed event is routed to the pending request's `onEvent` callback.

Important bridge event types include:

- `assistantTextDelta`
- `reasoningDelta`
- `progress`
- `toolRequested`
- `media`
- `voice`
- `usage`
- `sessionBinding`
- `error`
- `done`

`assistantTextDelta` is the main streaming text path. It becomes a webview message:

```ts
{ type: 'delta', role: 'assistant', text }
```

The webview receives that message and appends the text into the current assistant message card via `appendDelta(...)`.

The current visible streaming behavior is:

1. User submits a prompt.
2. Panel appends the user message and starts a timer.
3. Bridge streams assistant deltas.
4. Webview appends each delta into the latest assistant card.
5. Progress, tool, media, usage, and voice events render as separate UI elements.
6. On `done`, the panel marks the run finished, stops the timer, saves history, and drains any queued prompt.

Streaming also updates Advanced/Optimus indirectly. During a panel run, the extension accumulates live messages and writes `optimus-live-state.json`. The webview receives streaming through `postMessage`; Advanced/Optimus receives a throttled file mirror.

## Tool Execution

When the model requests local tools, the bridge emits `toolRequested`. The extension currently renders tool UI and executes tools locally from the extension host.

Read-only or parallel-safe tools can run in parallel. Other tools run sequentially and may require user approval unless the mode is `free`.

Supported local tool categories include:

- Read files.
- List directories.
- Glob, grep, and codebase search.
- Web search and fetch through the bridge.
- Image generation.
- Lints.
- Write, edit, and delete files.
- Create directories.
- Shell commands.
- REPL and code execution.
- Sleep.
- Task placeholder.

Shell output is streamed into the panel while the command runs.

After local tools complete, the extension sends `submitToolResult` back to the bridge. That can produce more assistant text or more tool requests, so the panel currently supports multi-step tool loops.

## Current History and State

The panel currently keeps and restores state through shared files under:

```text
~/.backboard_ide/
```

Important files:

- `config.json`: Backboard credentials and config.
- `panel-state.json`: latest panel state.
- `threads/*.json`: per-thread persisted panel state.
- `optimus-command.json`: commands from Advanced/Optimus to the right panel.
- `optimus-live-state.json`: live stream mirror for Advanced/Optimus.
- `optimus-metadata.json`: model and settings metadata for Advanced/Optimus.

The webview also periodically posts `syncPanelState` every two seconds so the extension can persist snapshots.

This means the current system is a mix of webview state, extension-host state, bridge state, and JSON files in the user home directory. The JSON files are part of the runtime contract between the right panel and Advanced/Optimus.

## Current Advanced/Optimus Integration

Advanced mode, internally called Optimus, currently does not directly control the webview through an in-process API. Instead, it writes a command file:

```text
~/.backboard_ide/optimus-command.json
```

The Backboard extension watches that file and also polls it every second. Supported commands include:

- `newChat`
- `showHistory`
- `showChat`
- `openHistoryEntry`
- `sendPrompt`
- `cancel`
- `refreshModels`
- `signIn`
- `reviewChanges`

When the right panel runs a prompt, it also writes live state to:

```text
~/.backboard_ide/optimus-live-state.json
```

This lets Advanced mode mirror the current prompt, status, streamed assistant text, running state, and workspace. Live-state writes are throttled to 120ms, with immediate writes for major state changes like send, done, cancel, and error.

The current relationship is:

- Right panel: owns bridge execution, prompt runs, tool calls, auth, model metadata, and panel history.
- Advanced/Optimus: opens as a standalone `vs/optimus` window, sends commands through `optimus-command.json`, reads metadata/history/live state through IPC backed by files, and can mirror or initiate Backboard work.

## Current User Experience

The current behavior is:

1. User opens the right panel.
2. If not signed in, they see an SSO gate.
3. Once authenticated, the panel loads settings, models, tools, and usage.
4. User types a prompt and optionally adjusts model, mode, and tools.
5. The panel starts a Backboard run.
6. Assistant text streams into the chat log.
7. Tool calls appear as grouped command/tool cards.
8. Terminal or long-running tool output streams incrementally.
9. Media, voice, usage, and questions render inline when returned by the bridge.
10. When complete, the run is saved to history and the queued prompt, if any, runs next.
11. Advanced/Optimus can observe or drive this same system through command and live-state files.

## Current Limitations and Shape

The current implementation has a few important characteristics:

- The panel UI is embedded in one large TypeScript file instead of a separate frontend app.
- Advanced/Optimus uses JSON files as a command/live-state bridge rather than a direct typed service API.
- The Optimus command file is watched and also polled, so command delivery is resilient but coarse.
- Live-state mirroring is throttled, so Advanced/Optimus sees near-live streaming rather than every raw webview delta.
- The right panel can execute a direct Optimus prompt path even when the webview is not visible.
- Model/tool metadata is cached and mirrored for Advanced/Optimus.
- The right panel is still the source of truth for actual Backboard runtime behavior.

In short, at the moment the right panel is the real Backboard runtime surface inside the editor. It owns the bridge connection, streaming, tool execution, persistence, auth, model metadata, and history. Advanced/Optimus is currently a standalone control and mirror surface layered on top of that runtime.
